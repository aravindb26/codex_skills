# Local Solodit Addendum: Signature Companion Mini-Skill

## Purpose
- Extend `audit-signature` with distilled High/Medium Solodit signature and authorization patterns.
- Do not replace `SKILL.md`, `reference.md`, or `checklist.md`.
- Use this for missing exploit shapes around session signatures, EIP-712 drift, ERC-1271/account-abstraction behavior, permit DoS, and signer-threshold systems.

## When To Use

Use after reading `audit-signature/SKILL.md` when code handles:
- EIP-712, permits, meta-transactions, session keys, signer gates, Safe modules, ERC-1271, EIP-7702 account behavior, signed prices, off-chain orders, or signed cross-chain messages.

## Companion Workflow

1. Load the original signature skill first.
2. Search current code with the extra terms below.
3. Build the exact signed message: domain, typehash, fields, nonce, deadline, chain, contract, signer, and action.
4. Compare signed fields to execution-time fields and mutable state.
5. Search Solodit stubs by signature type, domain/typehash, nonce variable, signer gate, and authorization function before escalating.

## Missing / Sharper Patterns To Check

### 1. Partial, session, or chained signature replay

Shape:
- A session/chained signature authorizes part of a call tree, but checkpoint, nonce, target, call data, or subcall constraints are incomplete.

Questions:
- Can a signed session call be replayed with a different subcall, checkpoint mode, or execution context?
- Are all nested calls bound to the same policy and nonce?
- Can disabling a checkpoint/checkpointer bypass validation for the chain?

### 2. EIP-712 typehash, domain, and digest drift

Shape:
- Code computes a digest that does not match the intended EIP-712 struct/domain, or domain fields do not match the deployed context.

Questions:
- Does the typehash exactly match the struct fields and order?
- Are chain id, verifying contract, name, version, salt, and fork behavior correct?
- Is the digest generated by standard EIP-712 flow or a custom shortcut?

### 3. Permit front-running and permit-induced DoS

Shape:
- A function expects to consume a permit then perform an action, but anyone can front-run the permit and cause the main operation to revert.

Questions:
- Does the protocol require `permit` success instead of tolerating already-used allowance?
- Can an attacker submit the same permit first to DoS liquidity, repayment, migration, or claim operations?
- Is Permit2 allowance/nonce state handled separately from protocol action state?

### 4. ERC-1271, EIP-7702, and account-abstraction edge cases

Shape:
- Contract signatures rely on `isContract`, codehash, ERC-1271 behavior, or account logic that can change or behave differently under account abstraction/EIP-7702.

Questions:
- Is `isValidSignature` called on the correct account at execution time?
- Can account code/logic change after signing but before execution?
- Does validation handle ERC-1271 magic values, reverts, gas grief, and non-compliant wallets?

### 5. Signer-gate, threshold, and Safe mismatch

Shape:
- A signer gate or module validates signers differently from the Safe/account that will execute the transaction.

Questions:
- Can signers add modules, change threshold, or swap owners inside the same transaction before checks reconcile?
- Is `validSignerCount` confused with configured threshold?
- Can address(0), stale signer ownership, too many modules, or off-by-one loops brick or bypass the account?

### 6. Successful action not stored or nonce integrity weak

Shape:
- The protocol verifies a signature but does not atomically mark the exact action/message/client id as consumed.

Questions:
- Is success recorded before external calls and across all replay routes?
- Can client id, request id, message id, or nonce be spoofed to suppress or replay actions?
- Is nonce scoped by signer, owner, account, chain, and action type?

### 7. Unsigned metadata changes execution meaning

Shape:
- Validity window, access level, recipient, amount, token, source account, signer role, calldata, price, slippage, or callback target is not signed but affects execution.

Questions:
- Which execution-time fields are not in the signed struct?
- Can attacker alter unsigned metadata while preserving a valid signature?
- Are off-chain assumptions about UI-filled metadata enforced onchain?

### 8. Signed price or oracle authorization injection

Shape:
- A signed price/update/message is accepted without binding signer role, asset id, market id, timestamp, nonce, or source domain tightly enough.

Questions:
- Can a valid signer for one asset/market authorize another?
- Can old signed prices be replayed into a new market state?
- Are price signers separated from admin/operator signatures?

## False-Positive Filters

Do not escalate unless:
- The signature path is reachable by an in-scope attacker or affects in-scope user funds/permissions.
- Missing fields can be attacker-controlled at execution time.
- Replay remains possible after considering nonce, deadline, chain id, verifying contract, and consumed-action state.
- ERC-1271/account-abstraction concerns affect supported wallets or program-relevant deployments.
- The impact is unauthorized action, fund movement, blocked user operation, governance/account takeover, replay, or rewardable DoS.
